# 设备、目录与坐标参考

本页定义资产存放位置、文件职责、版本身份和 TCP 坐标。配置操作见[日常指南](安装与日常使用.md)，字段填写见[套件说明](../kits/README.md)和[场景配置](场景处理.md)。

## 镜头术语

按相机在夹爪上的安装用途命名，不随拍摄内容或手的朝向改变：

| 统一名称 | 定义 | 现有接口标识 | 当前 X3 4K60 原始拼接画面 |
|---|---|---|---|
| 工作镜头 | 能看到夹爪的镜头 | `front` | 右半幅，1920×1920 |
| 环境镜头 | 相机另一侧的镜头 | `rear` | 左半幅，1920×1920 |

“左手/右手”区分两台相机；每台相机都有工作镜头和环境镜头。原片左右半幅描述像素布局，与左右手无关。

`front.mp4`、`front/`、`rear_calibration`、`shared_front` 等名称描述资产角色；front/rear 使用同一个 `install` 入口。工作镜头同样可以用于环境建图，地图的内容不决定镜头名称。

当前 X3 安装采用固定的工厂参数对应关系：`lens1`（第二组）是工作镜头，`lens0`（第一组）是环境镜头，原始编号保持不变。依据是 specialist 的参数解析与夹爪检测路径：第二组分配给它的 `rear`，夹爪标签也在 `rear` 中检测；因此两个项目的英文镜头命名相反：

| 统一名称 | 工厂参数 | 本项目 | specialist |
|---|---|---|---|
| 工作镜头 | `lens1` | `front` | `rear` |
| 环境镜头 | `lens0` | `rear` | `front` |

该对应关系用于当前 X3 安装与录制模式；参数缩放、裁切和外围投影精度仍通过诊断评估。镜头身份明确不等于工厂内参已通过实测验收。

```text
registry/                                   相机档案与实测标定
├── index.json                              设备状态与各镜头/来源的当前参数选择
└── cameras/<完整序列号>/
    └── calibrations/
        ├── front/<参数来源>/                 工作镜头当前参数
        └── rear/<参数来源>/                  环境镜头当前参数

recordings/calibration/<序列号>/<标定批次>/front/   全局标定原片

scenes/<场景>/
├── scene.yaml                              可选的场景参数覆盖
└── <采集批次>/                             各批次独立建图
    ├── batch.yaml                          用户声明套件及可选使用手/复用地图
    ├── mapping/                            本轮建图原片
    ├── pending/                            仅未分组原片的待配对区
    ├── .pipeline/                          程序维护的内部目录，无需查看；结果从 <任务>/results 进入
    │   ├── manifest.yaml                   当前设备、建图来源和绑定的地图版本
    │   ├── import.json                     最近一次有变化或问题的导入报告
    │   ├── maps/
    │   │   ├── versions/<地图版本>/        绑定、被保留运行引用的版本和最新一次建图
    │   │   └── cache/                      本批次建图缓存
    │   └── tasks/<任务>/
    │       ├── episode.yaml                原片引用和身份
    │       ├── state.json                  尝试和人工验收引用
    │       ├── cache/                      可重新生成的任务缓存
    │       └── runs/<运行>/                当前成功结果与最近一次尝试
    └── <任务>/
        ├── task.yaml                       可选：指令、使用手和同步
        ├── left/                           左手操作原片
        ├── right/                          右手操作原片（单手只需对应一侧）
        └── results -> ../.pipeline/tasks/<任务>/runs/<运行>/

kits/<套件>/
├── kit.yaml                                 可跨场景复用的左右设备和测量配置
├── tcp_camera.json                          当前安装的相机–TCP 变换
├── left_width.json                          可选：左手开口测量
└── right_width.json                         可选：右手开口测量
```

### 文件职责

| 对象 | 内容 | 操作者 |
|---|---|---|
| registry 测量资产 | 相机工作/环境镜头标定及其哈希 | 通过 umi-calib 登记和管理 |
| kit.yaml | 当前套件各手的设备、前后镜头参数来源与夹爪文件路径 | 手动填写 |
| tcp_camera.json | 当前安装的相机–TCP 变换和测量状态 | 手动维护，由 kit.yaml 引用 |
| left_width.json / right_width.json | 当前安装的像素—毫米锚点 | 手动填写实测值，由 run 直接读取 |
| scene.yaml | 可选模式、参数覆盖和环境海报布局引用 | 手动填写 |
| 环境海报布局 JSON | ID、字典、米制角点、来源与几何状态；与机身标定分开 | 根据排版与成品测量维护 |
| batch.yaml | 当前批次的套件、使用手和复用地图选择 | 手动填写 |
| .pipeline/manifest.yaml | 当前设备、建图输入和地图的解析记录 | 程序生成 |
| <任务>/task.yaml | 指令、使用手和同步 | 手动填写，可省略 |
| .pipeline/tasks/<任务>/episode.yaml | 原片身份与引用 | 程序生成 |
| .pipeline/tasks/<任务>/state.json | 处理尝试和人工验收的运行引用 | 程序生成 |
| .pipeline/tasks/<任务>/cache/ | 可重建的计算缓存 | 程序管理 |
| results | 指向当前成功运行的入口 | 成功后由程序发布 |

INSV 内部完整序列号用于识别设备，原文件名与内容保留。原片按 take 整理后直接引用；pending 中的原片确认归属并保存清单后才移除待配对副本。`.pipeline/tasks/<任务>/runs/` 只保留当前成功结果、最近一次尝试和验收记录的运行，被取代的运行在下次处理后删除；状态、清单、测量资产和成功结果共同用于有效性检查。

地图位于各批次 `.pipeline/maps/versions/<版本>/`，包含 manifest.json、maps/、devices/、map.json 和 report.txt。任务 episode.json 的 map 保存展示地图相对运行目录的路径与 SHA256。搬运批次时保留地图与任务的相对结构；独立交付可使用导出包。

## 身份与版本

| 对象 | 固定内容 | 何时新增 |
|---|---|---|
| 当前标定 | 按序列号、镜头和参数来源保存内参、外参、时差、验收及哈希 | 重新标定并 install |
| 海报布局 | 板内米制几何及来源；运行保存副本和内容哈希 | 打印尺寸、板内排列或标签尺寸改变时更新 |
| TCP 几何文件 | 套件内的安装变换与测量状态；结果保存文件副本 | 安装几何或夹爪改变时更新 |
| 宽度测量文件 | 套件内每手的像素—毫米锚点；结果记录内容与哈希 | 重新测量或安装变化时修改文件 |
| 套件配置 | 当前各手序列号、前后镜头来源、TCP 与宽度文件路径 | 换设备、换手或切换来源时更新 `kits/<套件>/kit.yaml` |
| 批次 | 当前套件选择、采集轮次与原片 | 新采集活动；配置调整可重跑原批次 |
| 地图版本 | 米制场景坐标、地图资产 | 建图输入变化或强制重建 |
| 任务 | 一次操作的原片与预期使用手 | 重新录制一次操作 |

registry 不为标定生成递增编号。每台相机按镜头和参数来源各保留一个当前目录，例如 `calibrations/front/measured/`；重新验收同一来源时原子替换该目录。相机资产校验完整 SHA256，历史运行使用自己的参数副本和哈希。新 YAML 只填写 front/rear 的参数来源选择；夹爪文件直接由套件维护，不另设编号。

套件名在项目内唯一，批次名在场景内唯一，任务名在批次内唯一。场景由目录确定，套件可跨场景复用；软件不能仅凭相机序列号识别拍摄场景。

当前配置与历史结果分别记录：run 读取 kit.yaml、batch.yaml 和 mapping 原片，生成本次快照；成功结果与失败记录保存当时的输入。单段建图引用直接保存 serial、path、sha256，dual 使用左右两段引用。修改当前配置的流程见[场景配置](场景处理.md#批次选项)。

registry/index.json 保存相机状态和各镜头/参数来源的当前选择；参数来源与资产哈希保存在当前资产的 manifest.json。套件分别选择 front/rear 的 measured 或 factory，后续运行自动解析当前参数；历史结果继续引用冻结身份和副本，不依赖登记目录的后续替换。夹爪配置没有全局默认值。

## TCP 坐标系

当前默认采用与 Genie omnipicker 机器人一致的机械轴向约定，标识为 `genie_omnipicker_axes_v1`。左右手使用相同的工具自身轴向定义。

### TCP 原点和三轴

原点是**夹爪闭合时，两指尖接触位置的中点**。相机到指尖的平移来自套件引用的几何文件。

| 轴 | 正方向 |
|---|---|
| +X | 从外侧指指向内侧指，用户确认内侧指位于工作镜头画面左侧 |
| +Z | 从夹爪本体指向指尖 |
| +Y | 按右手规则确定，即 `Y = Z × X` |

三轴固定在夹爪上并随它运动。+Z 使用本项目既有 CAD 中的本体到指尖方向，与工作镜头光轴约有 21.5° 倾角，不再与镜头朝向重合。位置和倾角仍是 CAD 名义值；轴向约定的统一不构成新的物理标定。

### 机器人依据与相机坐标

轴向依据 `genie_robot_description/urdf/G2_t2_crs/G2_t2_crs_omnipicker.urdf` 的 `gripper_l_center_link`、`gripper_r_center_link`：二者相对夹爪基座均绕 Z 转 −90°，因此 +X 沿基座 −Y、+Y 沿基座 +X、+Z 沿基座 +Z。基座中内侧指在 −Y，外侧指在 +Y。

URDF 中的 `camera_link` 是机械 link，其三轴与夹爪基座平行，并非本项目 X3 的光学坐标系。这里使用本项目的相机—指尖 CAD 外参和用户确认的手指方向计算旋转；没有将 URDF 的 `Rz(-90°)` 直接当作光学相机到 TCP 的旋转。

### 与 wholebody VR 数采的区别

wholebody 当前记录的是 `arm_l_end_link` / `arm_r_end_link` 的**末端法兰位姿**，尚未自动换算到 `gripper_*_center_link`。本项目 `trajectory.csv` 则已经通过相机到指尖的几何换算为**夹爪 TCP 位姿**。工具轴向约定相同，不代表两套输出记录了同一个参考点。

机器人实测与目标都需要先使用实际安装的 `T_end_tcp` 换算法兰到 TCP；随后再统一父坐标系或转换为一致的相对位姿表示。wholebody 新录制已将 VR 目标转换到 `base_link`；修复前的 `arm_base_link` 目标数据需单独核对和转换，字段定义见 wholebody 项目的 `docs/user/collect/schema.md`。

对于 `G2_t2_crs_omnipicker.urdf`，左右 `T_end_tcp` 的平移均为法兰系下 `[0, 0, 0.14918]` m；左侧旋转为单位阵，右侧旋转为 `diag(-1, -1, 1)`，即绕法兰 Z 转 180°。这里比较的是各侧法兰与该侧夹爪 TCP，左右夹爪自身仍采用相同的机械轴向定义。完整矩阵、固定关节来源、四元数顺序及正反换算见 wholebody 项目的 `docs/user/collect/schema.md`。

### 程序怎样计算

采用 `T_a_b` 将 b 系坐标变换到 a 系的约定。当前相机到 TCP 外参约为：

```text
R_camera_tcp ≈
[ -1   0           0          ]
[  0  -0.93041757 -0.36650123 ]
[  0  -0.36650123  0.93041757 ]

t_camera_tcp = [-0.0001815, 0.0369877, 0.1650461] m

T_scene_tcp = T_scene_camera × T_camera_tcp
```

旋转从原机械 CAD 定义导出：保留 +Z，将原 CAD 的 X、Y 同时反向以匹配“内侧指在画面左侧”的确认。相机中的指尖位置保持原值。资产只保存 `T_camera_tcp` 的旋转矩阵和平移；逆变换、四元数及杆臂长度在需要时计算，不重复保存。

### 与场景坐标系的关系

场景坐标系固定在环境中，+Z 朝上；TCP 坐标系随夹爪运动。

- `trajectory.csv` 的 `x y z` 是 TCP 原点在场景中的位置，单位米。
- `qx qy qz qw` 是 TCP 自身三轴相对于场景三轴的朝向。
- 双手使用同一地图版本时共享场景坐标。内部逐段轨迹引擎 的世界坐标每段分别建立。

场景到机器人基座的外参和控制器 TCP 配置需要另外确定。部署仍需确认控制器实际使用的工具坐标系。

### 几何资产

当前安装的几何由 kit.yaml 每手的 `gripper.tcp` 引用，例如 [kit_001/tcp_camera.json](../kits/kit_001/tcp_camera.json)。路径相对套件目录；左右安装一致时可以共用，不同时各用一份。运行入口读取并校验，计算前复制到运行目录；轨迹计算和来源报告复用已解析的几何，历史结果保留资产副本和哈希。

几何文件保存 `status`（测量状态）、`units`（固定为 `metres`）、`tcp_frame`（工具坐标约定）和 `T_camera_tcp`（TCP 坐标到相机坐标的变换）：

```text
T_camera_tcp.R_rows   3×3 旋转矩阵，按行保存
T_camera_tcp.t_m      TCP 原点在相机坐标系中的位置，单位米
```

场景输出按 `T_scene_tcp = T_scene_camera × T_camera_tcp` 换算，坐标轴说明也来自文件的 `tcp_frame`。不需要夹爪 manifest、版本号或 current 指针。相机标定验收不使用 TCP；独立逐段引擎仅在显式提供 `--tcp` 时生成 TCP 轨迹。

### 几何来源与验证状态

以下是从几何文件归入本文的工程记录，不参与运行时配置。

- `001` 的 CAD 定义日期为 2026-08-28；`002`、`003` 的轴向定义日期为 2026-10-26。三者的指尖位置完全相同：`[-0.0001815, 0.0369877, 0.1650461]` m；杆臂约 169.14 mm。`002` 只将工具轴改为工作镜头平行；`003` 保留原 CAD 的 +Z，翻转 X/Y 并将原 CAD 四舍五入后的旋转投影到 SO(3)。
- 原始来源为 SolidWorks 装配 `hardware/修改夹爪/夹爪整体装配.SLDASM`（2026-08-28 12:49）和 `Insta360 X3.SLDPRT`，分别以 TCP 和 CAM0 为输出坐标导出 `handheld_closed_in_TCP.step`、`handheld_closed_in_CAM0.step`。使用 7 个顶层部件锚点，通过集合差、成对距离特征匹配和不带缩放的 Umeyama 刚体拟合求解，历史复算脚本名为 `solve_t_tcp_camera_final.py`；STEP 文件 SHA256 记录在原运行日志中，当前仓库未附这些源文件。
- 原拟合 RMS 为 `5.355e-6` mm，最大残差 `7.525e-6` mm，尺度 `1.000000001`，旋转行列式为 1，正交误差 `1.33e-15`，往返误差 `1.11e-16` m。这些数值仅验证 CAD 坐标换算，不能代表实物精度。
- 相机系为工作镜头光学约定：+X 图像右、+Y 图像下、+Z 镜头向外。光学原点采用裸镜片外顶点后方 2.5 mm。依据是用户卡尺测得前后裸镜片顶点间距 31.1 mm，与 CAD 球面顶点 `z=+2.5000/-28.6000` mm 一致；INSV 厂家有效视点基线取 26.10 mm（field54 为 26.345 mm，field53 为 25.851 mm），深度按 `(31.1-26.10)/2=2.50` mm 估计。工作镜头镜片 CAD 球面半径为 24.7115 mm，球心位于 `z=-22.2115` mm，轴线偏差小于 `1e-4` mm。
- 早期 3.5 mm 深度来自将官方 33.1 mm 机身厚度视为裸镜片顶点间距的假设，已被卡尺和 CAD 取代。SolidWorks 原坐标实际已经建在 2.5 mm 深度，再向前修正 1 mm 会引入错误；因此旧 `depth_variant_2p5mm` 平移候选已废弃。源研究目录名为 `20260828_x3_optical_center_cover_research`。
- 光学原点深度不确定性暂按约 ±1.0 mm 估计：卡尺 ±0.2 mm、厂家基线参数差异 ±0.25 mm、前后对称假设 ±0.5 mm、有效视点变化保守项 ±0.75 mm。相机滚转和 X 方向与真实图像读出的关系仍需核对；+Y 向下已有手指出现在画面底部的观察支持。机械轴 +X 的符号依据是用户于 2026-10-26 确认内侧指位于工作镜头画面左侧。
- 机器人参考文件 `genie_robot_description/urdf/G2_t2_crs/G2_t2_crs_omnipicker.urdf` 的记录 SHA256 为 `bc9b980a1085b326ff2f5bb04726a0a57a5c3e79a6020e6520da27a2bb55be36`；参考 TCP link 为 `gripper_l_center_link`、`gripper_r_center_link`。原始 `001` CAD JSON 在精简前的 SHA256 为 `1e17a28aed1c84ba967eded53f7798fa1f233ac0212c9cce808dae03e2b74b5d`，此处只作历史来源记录；归档文件保留原版本的 `manifest.json`，当前运行按自己的资产快照与哈希追溯。
- 历史候选 `URDF/frames_candidate.yaml` 中的 `t_tcp_camera=[0,0.06,-0.10]` m、单位旋转和 `calibration_id=UNSET` 是另一份占位参数，杆臂约 116.6 mm，与这里的约 169.1 mm 和 21.5° 倾角不一致，未用于本项目的光学到 TCP 换算。

所有版本继续标记为 `NOMINAL_CAD_CANDIDATE_UNVERIFIED`。需要指尖治具、AprilGrid 或手眼加 pivot 等独立实物验证后才能改变该状态；字段整理不能替代实物测量证据。

## 历史资产与迁移

任务原片放在 `take_*/left/`、`right/` 下，同侧存在多段不同原片仍需人工核对。清单统一从批次 `.pipeline/` 读取，旧清单位置、`take_*/videos/` 和场景 schema 2 已退役；继续处理旧数据时，新建批次并按当前模板放入原片，任务人工选项填入 `task.yaml`。历史结果格式和当前布局下的批次 schema 4 仍可读取；历史流程变更见[来源记录](dev/PROVENANCE.md)。

### 夹爪几何版本

旧资产不可覆盖，各版本按自己的定义读取：

| 版本或约定 | TCP 轴向 |
|---|---|
| `001` | 原机械 CAD 轴，开合方向正负未与机器人对应 |
| `002` / `front_optical_parallel_v1` | 与工作镜头平行，+X 图像右、+Y 图像下、+Z 镜头前方 |

这些历史文件完整归档在 `hardware/grippers/archive/handheld_v1/001/`、`002/`、`003/`；旧 current.json 只保留作历史记录，不参与运行。TCP 原点位置相同，姿态约定不同。迁移时将 003 的原始几何复制到 kit_001/tcp_camera.json，矩阵和未验证状态保持不变。运行只读取 kit.yaml 引用的文件；更新文件后重跑批次才采用新值，已有结果保留自己的副本。

### 当前参数与历史资产

每个镜头、每种参数来源只有一份当前选择，统一的 `install` 自动识别 front 结果目录或 rear 结果目录/`rear_calibration.json`，更新对应的固定目录。kit 不填写版本号；新运行解析并冻结当前参数。历史运行使用自己的参数快照。

## 环境海报资产的职责与变更

| 层级 | 保存什么 | 不放什么 |
|---|---|---|
| `registry` 的 front / rear 当前标定 | 本设备各镜头完整测量、参数来源、验收及哈希 | 海报布局或海报在房间中的位置 |
| `kit.yaml` | 当前手与序列号、front/rear 的来源选择、TCP 等安装文件 | 每段录像的海报位姿 |
| `scene.yaml` → 布局 JSON | 字典、ID、米制角点、PDF 来源与 `geometry_status` | 相机外参、可跨任务固定的海报世界位姿 |
| 地图/任务/独立运行结果 | 当次冻结测量、布局、检测证据、求解状态和海报位姿 | 对未来运行生效的隐式新默认值 |

registry 不为工作镜头或环境镜头生成递增编号。套件使用同一设备、所选参数来源匹配的当前标定。当前没有单独的“前后镜头组合验收”资产，两个当前标定一起被选中不等于组合已通过实拍海报验证。

没有绑定正式 rear 而需要海报/dual 时，运行结果可保存 `umi_rear_factory_fallback`：从当前 X3 INSV 的工厂参数与本设备 front B 推导 rear，沿用 front 时差并记录共享帧时钟假设。它属于当次运行资产，标记 `NOT_EVALUATED`，不写入 registry 当前目录或修改 kit。正式绑定有误时拒绝；工厂参数发生变化也会改变资产哈希，地图与任务仍需匹配。[标定指南](标定.md#双镜头标定与海报接入)说明适用范围与独立 rear 验收流程。

- 海报在两段录像之间整体移动：不重标相机，不改变板内布局；每段重新估计位姿。单段录像内移动违反静态板假设。
- 重印、重新粘贴或发现尺寸错误：更新布局并保留测量记录；改变布局内容会使相关计算身份变化。参与建图尺度时重建受影响的地图，任务也需重新计算；只有任务标签使用布局时不要求因此重建未使用海报的地图。
- 更换或重新验收镜头测量：重新 install 同一来源并核对地图与任务的标定绑定；安装会替换同镜头、同来源的当前目录。
- 拆装相机与夹爪：先检查 TCP 等安装几何；不能将机身内参、外参的重标定与夹爪安装测量混为一项。

海报当前 `pdf_design` 表示仅核对排版，`physically_measured` 必须有成品测量依据。现有布局读取器不接受任意新增字段；测量日期、工具、横纵尺寸等可先另存记录，正式证据引用格式尚待补齐，不能只改状态就声称测量完成。

完整操作流程见[双镜头标定与海报接入](标定.md#双镜头标定与海报接入)。
