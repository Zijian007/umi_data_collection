# 原理与精度：轨迹工具怎么算的、验证到了什么程度

> 给想知道"结果能不能信、信到什么程度"的人看。怎么录见 [`录制说明.md`](录制说明.md)，怎么用见 [`使用说明.md`](使用说明.md)。
> 文中 `dev:experiments/...` 指开发分支 `dev` 上的证据文件。

## 1. 怎么算的

一段 X3「360 4K60」录像里有两样东西：左右并排的两个鱼眼画面（59.94 帧/秒），和约 1000 Hz 的 IMU（陀螺 + 加速度计）。
工具 `umi-traj` 对每段录像依次做：

1. **读时间戳和 IMU**（`software/trajectory/x3_extract.py`）：从原始文件的容器里读每一帧的时间戳（不解码画面），从文件尾部读 IMU；
   每隔一帧取一帧（29.97 帧/秒），IMU 与画面放到同一个时钟上。检查录制模式、IMU 是否完整、相机有没有丢帧。
2. **裁出前镜头视频**（`make_lens_video.py`）：取夹爪正对的那一侧鱼眼中间 1440×1440，缩到 720×720。
3. **建图**（ORB-SLAM3 纯视觉单目，`x3_mono_slam`）：用整段视频建一张环境地图；建图时把画面里夹爪手指的位置涂黑（`config/front_hand_mask.png`），
   免得手指被当成环境。转开太久跟丢时，ORB-SLAM3 会另起一张图，所以一段录像可能有好几张图。
4. **定位**：把每一帧放回**每一张**地图里重新定位，按帧合并（当前图跟得上就不换，否则换到最大的那张图），记下每帧来自哪张图。
5. **和 IMU 融合**（`kiwi_fuse3s.py`，GTSAM 因子图）：
   - 地图是"等比例"的，没有真实尺寸，也不知道哪边朝下。先用 IMU 给每一段连续跟踪估出尺度和重力方向，
     并检查"这段视觉轨迹和 IMU 自洽吗"（尺度为正、足够多对、波动 ≤ 20 %、重力 9.81 ± 0.5 m/s²）。
   - 这个检查是同一镜头所有段一起解的（共用一个加速度计零偏），一段坏的会把好的也拖下水。所以长段（≥ 16 s）没通过时，
     先单独检查它；单独也不过，就从中间切开、两半再分别检查，直到把坏的那一截孤立出来（2026-10-07 加入，见 §3）。
   - 自洽的段用位置和朝向约束轨迹，不自洽的只用朝向。同一张图里尺度一致的段共用一个摆放（转开再回来的前后两段因此接得上）。
   - 静止时加零速约束。IMU 把所有帧连成一条连续、米制、重力对齐的轨迹，从第一帧起就有位姿。
6. **换算到夹爪**：IMU 轨迹 × 相机–IMU 标定 → 相机轨迹；× 相机–TCP 几何（CAD）→ 夹爪 TCP 轨迹。

方法思路来自 KIWI（arXiv 2609.22809）：每个镜头自己建图、逐帧重定位、离线和 IMU 融合。KIWI 的代码没有公开，方程和实现是我们自己的。
默认只用前镜头（`--mode handheld`）：手持时后镜头大多拍到操作者本人，实测不可靠。装在机械臂上、后镜头看得到房间时，可以用 `--mode dual`。

## 2. 精度证据

**参考真值**：录像时在场地里固定一块 AprilGrid 标定板。前镜头看到板的帧，用板单独算出相机位姿作参考，参考和被测算法无关。
做一次全局刚体对齐（只平移和旋转，**不拟合尺度**，所以尺度误差也算在内）后算轨迹误差（ATE，均方根）。机械臂上的录像用机械臂自身的运动学做参考。

### 2.1 手持录像（8 段，前镜头 + IMU）

| 段 | 内容 | 此前用的 OpenVINS | 本工具的方法 |
|---|---|---|---|
| E (030) | 盲评段 | 8.81 mm | **7.34 mm** |
| 064 | 正常操作 | 7.45 mm | **3.29 mm** |
| 066 | 正常操作 | 7.54 mm | **4.72 mm** |
| 067 | 预注册测试：正常操作 | 12.90 mm | **4.15 mm** |
| 068 | 预注册测试：剧烈动作 | 39 m（发散） | **4.04 mm** |
| 069 | 预注册测试：转离视野再回来 | 114 m（发散） | **5.33 mm** |
| 070 | 转离再回来 | 65.8 mm（尺度错 44 %） | **6.65 mm** |
| 071 | 转离再回来 | 10.39 mm | **7.66 mm** |

出处：`dev:experiments/reviews/20261003_kiwi_reloc_fix_and_ov_divergence.md` §1d、
`dev:experiments/reviews/20261003_kiwi_dual_handheld_test.md`（067–069 的预注册测试）。

### 2.2 装在机械臂上（2 段，前后两个镜头 + IMU）

轨迹长度与机械臂实测之比（越接近 1 越好）：042 **1.005**（OpenVINS 1.050），045 **0.995**（OpenVINS 0.941）。

### 2.3 这些数字的分量（实话）

- 067–069 三段是**预注册测试**（方法、参数、判定规则在看数据之前提交），n = 3，三段都判"优、无任何一项劣"。
- 其余是方法开发时已经看过的数据，属于开发性证据。069 的修复（多地图定位 + 同图分组）是看过 069 之后做的。
- **状态**：这是**候选方法**。项目里正式冻结、验收过的 VIO 仍是 OpenVINS v2.1；本方法还没有走完正式验收（独立盲评）。
  交给外部使用是项目负责人的决定，依据就是上面这些证据。
- 相机–TCP 几何是 CAD 名义值（`NOMINAL_CAD_CANDIDATE_UNVERIFIED`）：上面的精度说的是**相机 / IMU 轨迹**；
  TCP 轨迹还要再加上 CAD 与实物之间的偏差（目前没有独立实测）。

## 3. 这个安装包和验证时用的是不是同一个东西

上面的证据是在实验室服务器（lab0）上的环境里跑出来的。打包成"任意 Linux 一键安装"后，我们逐项核对了：

| 环节 | 和验证版的关系 | 核对方式 |
|---|---|---|
| 融合、裁视频、合并定位结果的脚本；ORB-SLAM3 配置；遮手图；标定文件 | **逐字节相同** | sha256，`dev:software/trajectory/tests` 钉住 |
| 读时间戳和 IMU | 新写的（不再解码整段视频、不再写几 GB 的 PNG），输出**逐字节相同** | 7 段录像的帧时间戳文件和 IMU 文件与原转换器逐字节比对 |
| GTSAM | 验证时用的 nightly 版会被 PyPI 删掉，改用正式版 4.3.0 | 22 个存档融合用同样输入重跑：19 个轨迹**逐字节相同**，3 个（NERO 045、069 两种模式）只差浮点舍入（位置最大差 0.000001 mm） |
| FFmpeg 8.0.1、OpenCV 4.12.0、Boost、Eigen | 与验证环境**同一构建**（conda-forge 锁定清单） | 包的构建号一致 |
| 裁视频用的 x264 编码器 | 验证时实际用的是服务器系统自带的 FFmpeg 4.2.7（x264 155），安装包里是 FFmpeg 8.0.1（x264 164），**裁出的视频不逐字节相同** | 下面的整段回归 |
| ORB-SLAM3 | 同一份源码（cheng-chi/ORB_SLAM3 @ b741dca3）+ 同样两处补丁，编译器 GCC 11.4（验证时 GCC 9.4），**二进制不同** | 下面的整段回归 |

ORB-SLAM3 本身多线程、每次跑结果都有小幅波动，所以最后一关是**用安装包从头重跑全部手持录像、用同一个打分器打分**：

| 段 | 验证时（lab0，单次） | 安装包从原片重跑（同一打分器、同一板参考） |
|---|---|---|
| 064 | 3.29 mm | 3.30 mm |
| 066 | 4.72 mm | 4.55 mm |
| 067 | 4.15 mm | 4.24 mm（另两次重复：4.19、11.95 mm） |
| 068 | 4.04 mm | 3.95 mm |
| 069 | 5.33 mm | 5.14 mm；7 次重复 5.1–16.8 mm |
| 070 | 6.65 mm | 6.91 mm；3 次重复 6.9–28.6 mm |
| 071 | 7.66 mm | 7.71 mm |

最后一关：**从 GitHub 全新 clone、空环境从零安装（6 分钟）、用 `umi-traj` 处理**（自动重新建图开着）：
067 **4.20 mm**（一次建图）、069 **5.39 mm**、070 **6.83 mm**（这两段各建图 3 次取最好），与验证结果同级。

几点要知道：

- **同一段每次跑结果不完全一样**。ORB-SLAM3 建图是多线程的，地图在哪里断开、断成几块每次不同；常规录像差别很小，
  "转开十几秒再回来"的录像（069、070）差别可以到几倍。验证时的数字也只是一次运行。
- 打包回归时发现，在不走运的那几次里，069 / 070（以及一次 067）会整段失败或误差到米级——用验证时的原环境原样重跑也一样，
  是方法本身的薄弱处。为此加了两道保险（2026-10-07）：融合时把坏的那一截单独孤立出来（上面第 5 步），
  以及 `umi-traj` 发现结果可疑时自动重新建图、最多 3 次取最好（见 [`使用说明.md`](使用说明.md) 第 4 节）。上表的重跑数字都是加了第一道保险之后的。
- 在验证过的其他录像上，这两处改动不改变任何结果（20 次存档融合重跑，同版本下逐字节相同）。

## 4. 已知限制

- **两份标定各管各的。** 相机标定（内参、镜头与机内 IMU 的关系、时间差）属于那一台相机，拆装不影响它；换了另一台相机要重新标定（`./umi-calib`，见 [`标定说明.md`](标定说明.md)），否则没有精度保证。相机–夹爪几何只在夹爪尖合拢时相对镜头光心的位置变了（换夹爪、换安装件、改相机安装位置或角度）时才需要重做。
- **只支持 X3「360 4K60」录制模式。** 标定就是在这个模式、这个裁剪区域上做的。
- **持续剧烈转动会丢跟踪**（每秒半圈以上、持续数秒）：中间丢一段能靠 IMU 和"回到同一张图"衔接（068、069 都是这样救回来的）；
  如果开头扫图那段就丢，整段可能失败。
- **每段录像的世界坐标系是独立的**：原点和水平朝向任意，不同录像之间不能直接比坐标。
- **相机丢帧的录像**默认不处理（`--allow-irregular` 可以强行处理，未经验证）。目前所有测试录像都没有丢帧。
- **只输出轨迹**：夹爪开合宽度、LeRobot 数据集、训练和机械臂部署在开发分支上，还没有到交付状态。
