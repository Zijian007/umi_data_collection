# UMI 场景流水线重构会话总结

更新时间：2026-11-14

本次工作在 `refactor/pipeline-epochs-sync` 分支完成，重点是把场景采集、地图阶段、任务轨迹抽取和测试夹具收口到同一套数据模型。当前实现以 `collection.yaml` 和 `.pipeline/` 为准，旧的用户配置文件不再作为正常入口。

## 本次完成的工作

### 1. 测试夹具统一到 collection schema

- 场景和批次夹具统一写入 `collection.yaml`。
- 任务配置统一写入所属批次的 `collection.yaml.tasks`。
- 测试辅助函数新增任务配置的读写入口，避免测试直接创建 `task.yaml`。
- 删除依赖旧目录结构、旧共享解码假设和无效伪 INSV 的多余测试。
- 保留的 `scene.yaml`、`batch.yaml`、`task.yaml` 只用于验证旧格式会被明确拒绝。

### 2. 已绑定地图的批次不会在任务运行时偷偷重建

- 任务运行前会读取批次内部清单中的冻结地图指针。
- `mapping/` 已被整理或清理时，只要地图仍有效，后续 take 仍可运行。
- 专家参数覆盖不会改变已绑定地图的坐标系。
- 地图资产被篡改、地图清单哈希不匹配或地图配置发生变化时，运行会拒绝并要求显式重新 build。
- 这解决了“任务运行时因为输入不完整而误建新图”和“地图损坏后被自动覆盖”的拧巴行为。

### 3. 多地图和地图选择规则

- 地图按 epoch 保存为不可变版本。
- 默认策略是 `latest_prior`：每个 take 使用采集顺序上距离自己最近的已建地图。
- 任务级 `map_version` 或 `map_epoch` 可以显式固定地图。
- 多 epoch 可以通过规划、建图和任务运行流程处理；排序存在歧义时不会自动猜测。
- 不同地图 epoch 默认保持独立坐标系，不因为环境标签 ID 相同就自动拼接坐标系。

### 4. audio_auto 采用 specialist 的 session-clock 约定

- 音频同步使用包络相关估计相对偏移，并保留峰值、峰值比和输入指纹。
- `sync.json` 记录 `status: ready` 后才能进入轨迹抽取。
- 偏移会按照 specialist 约定同时作用于视频、IMU 和曝光时间轴。
- 录像指纹变化、同步失败或记录不完整时会拒绝复用旧结果。
- 已有旧的中间同步记录可以转换为 specialist 语义的 ready 记录。

### 5. 报告和缓存审计

- 任务报告包含地图版本、地图坐标系、镜头来源、环境标签策略和坐标变换链。
- `frames.csv` 记录逐帧的视觉镜头、地图角色、地图索引、视觉约束或 IMU 推算来源。
- 正式报告会汇总逐帧来源，并区分视觉约束帧和主要依靠 IMU 的帧。
- 缓存审计统一支持：`reused`、`computed`、`invalidated`、`failed`、`skipped`、`not_applicable`。
- 同步、标定、TCP、夹爪检测、标签检测和轨迹阶段可以记录缓存键、路径和复用原因。

## 当前用户侧工作流

日常场景配置写在批次的 `collection.yaml`：

```yaml
schema_version: 1
scene:
  layout: auto
  map_reference_arm: left
kit: kit_001
arms: [left, right]
map_policy: latest_prior
tasks:
  take_001:
    instruction: 拿起物体并放到指定位置
    expected_arms: [left, right]
    synchronization: assumed_simultaneous
```

典型流程为：

1. 将建图录像放入 `mapping/`，任务录像放入 `take_xxx/left/` 和 `take_xxx/right/`。
2. 执行 `umi-scene build <批次>` 建立或更新地图。
3. 执行 `umi-scene run <批次>` 抽取任务轨迹。
4. 新建地图后，后续 take 默认选择此前最近的地图 epoch。
5. 通过 `umi-view` 查看轨迹、地图、逐帧来源、同步和缓存报告。

硬件套件和相机标定仍由 kit、registry 管理；`collection.yaml` 负责场景、批次和任务事实。算法数值仍由公共配置和专家覆盖控制。

## 仍待优化的点

### P0：真实 INSV 音频同步验收

当前已经具备自动生成 ready `sync.json` 的代码路径，但还缺真实设备数据验收：

- 不同相机型号和录制模式的 A/V 固定延迟资产。
- specialist 的 landmark voting、漂移估计和置信度规则与真实 INSV 的对照。
- 长录像、弱音频、周期性声音和音频缺失时的拒绝阈值。
- 一套可重复运行的真实双镜头同步回归集。

当前 `specialist_assumed_video_clock` 表示采用 specialist 的统一 session-clock 假设，不等于已经完成所有录制模式的硬件 A/V 延迟标定。

### P0：跨 epoch 坐标对齐

当前的安全策略是不同 epoch 各自拥有独立 `frame_id`，不允许直接叠加。若业务要求跨 epoch 轨迹进入同一坐标系，需要新增：

- 固定锚点协议和锚点资产版本。
- 锚点位置稳定性检测。
- 地图间 `T_scene_map` 变换的估计和验收。
- 锚点移动、替换、遮挡或检测不足时的拒绝逻辑。

在没有稳定锚点和验收规则前，不建议自动做跨 epoch 变换。

### P1：真实场景端到端回归

需要建立一套受控的真实数据集，至少记录：

- 原片指纹和采集顺序。
- 相机、前后镜头和 TCP 标定版本。
- 地图 epoch、环境标签布局和标签物理尺寸。
- 视觉覆盖、IMU 约束、尺度误差、地图定位误差和双手一致性。
- 同一输入重复运行的输出差异。

目前完整单元测试已经收口，但合成夹具不能替代真实 INSV、真实环境标签、真实夹爪和真实 TCP 几何验收。

### P1：环境标签的真实测量与策略验收

检测、尺度和融合三个开关已经统一为独立语义：

- `detection`：是否运行环境标签检测。
- `scale`：是否允许环境标签参与尺度估计。
- `fusion`：是否允许环境标签参与任务轨迹融合。

仍需用真实海报和真实环境镜头确认远距离小标签、部分遮挡、视场边缘、标签移动以及多地图阶段中的拒绝行为。PDF 设计尺寸也需要替换为成品实测证据后，才能宣称物理尺度已经验收。

### P1：夹爪宽度和 TCP 几何

- 只有两标签中心距的套件不能直接生成夹爪开合宽度，仍应保持 `training_ready: false`。
- 需要为实际夹爪补做像素到毫米的宽度标定。
- 相机到 TCP 的几何目前仍可能使用 CAD 名义值，需要独立测量并冻结证据。

### P2：单 YAML 的边界继续收口

当前已经移除日常使用中的 `scene.yaml / batch.yaml / task.yaml` 拆分，场景、批次和任务事实统一到 `collection.yaml`。如果“单 YAML”进一步要求把 kit、相机标定选择和所有算法数值也放进同一个用户文件，还需要重新定义资产所有权：

- 场景和任务事实属于 `collection.yaml`。
- 设备、标定和 TCP 属于 kit/registry。
- 算法数值属于公共配置，专家覆盖只用于排障。

建议保留这三类边界，避免把不可变设备资产和每批采集事实再次混在一起。

### P2：一键 epoch pipeline 的真实批次验收

代码已经提供规划、建图和运行的组合入口，但还需要在真实批次上确认：

- 录像时间戳排序是否足够稳定。
- 新地图插入后 take 的最近前序地图选择是否符合现场预期。
- 中途失败后重跑是否只重做必要阶段。
- 规划清单、地图版本和任务报告之间是否能被查看器完整呈现。

## 后续建议顺序

1. 用真实双镜头 INSV 完成 audio_auto 验收和录制模式延迟资产。
2. 建立真实场景端到端回归集，覆盖地图更新、环境标签和夹爪测量。
3. 决定是否需要跨 epoch 统一坐标系；只有业务确实需要时再实施固定锚点。
4. 在真实批次上验收一键 epoch pipeline。
5. 最后再决定是否把 kit/registry 的选择进一步收进单一用户 YAML。
