# 使用说明：安装，丢进录像，拿到轨迹

> 怎么录见 [`录制说明.md`](录制说明.md)；原理和精度见 [`原理与精度.md`](原理与精度.md)。

整个流程都在你自己的电脑上跑，不需要连我们的服务器，也不需要 GPU。

---

## 1. 需要什么样的电脑

| 项 | 要求 |
|---|---|
| 系统 | **64 位 Linux（x86_64）** 直接装：已实测 Ubuntu 20.04 和 22.04，更新的版本应该也行但没有实测；**Windows / macOS** 用 Docker（第 3 节） |
| CPU / 内存 | 4 核以上、8 GB 内存以上；一段一分钟的录像大约用 4 个核跑几分钟 |
| 磁盘 | 安装约 5 GB；处理时每段录像临时占用约 1 GB（跑完自动删掉，只留结果，每段几 MB） |
| 网络 | 只有**安装时**要联网：github.com、conda.anaconda.org、pypi.org。处理录像不联网 |
| 权限 | 本机安装**不需要 sudo**，不改系统设置，所有东西装在仓库里的 `.deps/` 目录，删掉它就是卸载 |

## 2. Linux：本机安装（推荐）

```bash
git clone https://github.com/Torbjorn-s-Apple-Americano/umi.git
cd umi
bash install.sh
```

`install.sh` 会依次：下载 conda 包管理器（micromamba，校验 sha256）→ 按锁定清单装好 Python、FFmpeg、OpenCV、编译器等
→ 装 GTSAM → 从源码编译 Pangolin 和 ORB-SLAM3 → 自检。最后一行出现 `ALL OK` / `安装完成` 就好了。

- 首次安装 15–40 分钟（主要是下载和编译）。中途断了直接重跑 `bash install.sh`，做完的步骤会跳过。
- 每一步的完整日志在 `.deps/logs/`；失败时屏幕上会打印出错那一步日志的最后 30 行。
- 想装到别处：`UMI_DEPS=/data/umi-deps bash install.sh`（之后运行时也要带同样的 `UMI_DEPS`）。
- 编译默认按本机 CPU 优化（`-march=native`），所以 `.deps` 不要拷到另一台 CPU 不同的机器上用，在那台机器上重新装。

随时可以检查安装：

```bash
./umi-traj check
```

## 3. Windows / macOS / 不想装在本机：Docker

需要先装好 Docker（Windows / macOS 用 Docker Desktop）。在仓库目录里：

```bash
docker build -t umi-traj .
```

（一次，15–40 分钟。镜像里用的是和本机安装完全相同的 `install.sh` 和锁定清单。）

处理录像时把放录像的文件夹挂进容器的 `/data`：

```bash
docker run --rm -v /path/to/videos:/data umi-traj /data
```

Windows（PowerShell）：

```powershell
docker run --rm -v D:\videos:/data umi-traj /data
```

结果出现在录像文件夹里的 `umi_traj_out\`。Linux 上建议加 `--user "$(id -u):$(id -g)"`，结果文件就归你而不是 root。

- 镜像在哪台机器 build 就在哪台用（按本机 CPU 优化编译）。要把镜像拷给别的机器，build 时加
  `--build-arg ORB3_MARCH=x86-64-v2`。
- Docker Desktop 默认可能只给容器 2 个 CPU / 2 GB 内存，在 Docker Desktop 设置里调到 4 核 / 8 GB 以上。

## 4. 处理录像

把 `.insv` 放进一个文件夹（比如 `~/umi_videos/`），然后：

```bash
./umi-traj ~/umi_videos
```

- 也可以只给一个文件：`./umi-traj ~/umi_videos/VID_20261003_182246_00_067.insv`
- 结果默认写到输入旁边的 `umi_traj_out/<录像名>/`；指定位置用 `--out 目录`。
- **已经成功处理过的录像会自动跳过**：以后有新录像，直接丢进同一个文件夹再运行一次就行。要重算加 `--force`。
- 多段录像同时跑：`--jobs 2`（每段大约占 4 个核，8 核电脑用 2，16 核以上可以 3–4）。
- 屏幕上每段会显示三步进度：读时间戳和 IMU → 建图、定位、融合（几分钟）→ 写结果。
- 如果看到 `try 1: ... -> mapping again`：ORB-SLAM3 每次建图都不完全一样，这一次的结果看起来不可靠（地图被分成几块各自摆放，
  或者不到 95 % 的帧在地图里定到了位置），工具会自动重新建图，最多 3 次，留下最好的一次。常规录像一般一次就过；
  转开很久再回来的录像经常要 2–3 次，耗时相应翻倍。

其他选项（`./umi-traj --help`）：

| 选项 | 作用 |
|---|---|
| `--mode dual` | 前后两个镜头都用。适合装在机械臂上、后镜头能看到房间的录像；手持录像用默认的 `handheld`（dual 模式在这个安装包上还没有整段回归过） |
| `--max-tries N` | 结果看起来不可靠时最多建图几次（默认 3；1 = 只跑一次、最快） |
| `--keep-work` | 保留中间文件（裁出来的镜头视频、地图），排查问题用 |
| `--allow-irregular` | 相机丢过帧的录像默认不处理；加这个按真实帧时间处理（未经验证） |

## 5. 结果是什么

每段录像一个文件夹：

```text
umi_traj_out/VID_20261003_182246_00_067/
  traj_tcp.txt       夹爪参考点（TCP）的轨迹  <- 一般用这个
  traj_camera.txt    前镜头相机的轨迹
  traj_imu.txt       IMU 的轨迹（融合的原始输出）
  frames.csv         每一行轨迹对应视频第几帧、靠什么定的位
  summary.json       这段录像的概况和检查结果
  trajectory.png     一眼看结果：俯视图、侧视图、位置随时间
  logs/              各步骤日志（出问题时看这里，或发给我们）
```

### 轨迹文件格式（三个 `traj_*.txt` 一样）

TUM 格式，`#` 开头是说明，之后每行一个位姿：

```text
t  x  y  z  qx  qy  qz  qw
```

- **t**：视频里的时间（秒），视频第一帧 = 0。每秒 29.97 行：第 k 行对应原视频（59.94 帧/秒）的第 2k 帧。
- **x y z**：位置，单位**米**。
- **qx qy qz qw**：朝向四元数（w 在最后）。位姿的意思是"把这个物体坐标系里的点变到世界系"。
- **世界系**：z 轴朝上（和重力相反），真实尺寸；**原点和水平朝向每段录像各自任意**，所以只有同一段录像内部的相对运动有意义，不同录像之间的坐标不能直接比。
- **TCP**：夹爪的操作参考点。相机到 TCP 的几何来自 CAD 名义值（状态 `NOMINAL_CAD_CANDIDATE_UNVERIFIED`，还没有独立实测核验）。
- **相机系**：x 向右、y 向下、z 向前（镜头朝向）。

### frames.csv

| 列 | 意思 |
|---|---|
| `row` | 轨迹文件的第几行（从 0 起） |
| `video_frame` | 原视频的帧号（= 2 × row） |
| `t_video_s` | 同轨迹文件的 t |
| `constraint` | 这一帧的位置靠什么定：`full` = 相机在地图里定到了位置；`rot` = 只定到了朝向；`imu` = 相机没定到，靠 IMU 推算衔接 |
| `front_lens_tracked` | 前镜头这一帧有没有在地图里定位成功（1/0） |

### summary.json 里值得看的几项

| 字段 | 意思 |
|---|---|
| `status` | `ok` 或 `failed`；失败时 `reason` 写原因 |
| `constraint_fraction.full` | 有多少比例的帧由相机地图定到了位置（越高越好；我们验证过的录像在 0.85–1.0） |
| `longest_stretch_without_map_position_s` | 最长一段没有地图位置、靠 IMU 衔接的时长（秒）。几秒以内且两头都回到同一张地图时问题不大 |
| `tracking.front_map_build_tracked` | 建图时跟上了多少帧 / 总帧数 |
| `tcp_path_length_m`、`tcp_extent_m` | TCP 走过的路程、活动范围（米），用来和你记得的动作大致对一下 |
| `tries`、`chosen_try` | 建了几次图、每次的地图摆放块数和有地图位置的帧比例、最后用的是第几次 |
| `notes` | 自动检查发现的问题（经验规则，不是精度测试） |

## 6. 出问题怎么办

| 现象 | 多半是因为 | 怎么办 |
|---|---|---|
| `还没安装：先运行 bash install.sh` | 没装或 `.deps` 被删了 | 运行 `bash install.sh` |
| 安装时下载失败 | 网络访问不到 github.com / conda.anaconda.org / pypi.org | 换网络或配代理（`https_proxy=...`）后重跑 `bash install.sh` |
| `REFUSED: ... profile ...` | 不是 360 4K60 模式录的 | 相机改成 360 视频 4K60 重录 |
| `REFUSED: ... IMU trailer unreadable` | 文件被导出/剪辑过，或拷贝不完整 | 用相机里的原始 `.insv` 重新拷 |
| `frame timing is irregular` | 相机录制时丢帧 | 可以加 `--allow-irregular` 试算（未经验证），或重录 |
| `MAP_FAILED front` | 建不起地图：画面太糊/太暗/对着白墙，或开头没有移动 | 按录制说明第 3 节重录 |
| `FUSE_FAILED ... NO_USABLE_LENS` | 跟踪片段都没通过 IMU 一致性检查：多半开头扫图时只转不挪、或录像太短 | 开头扫图时多带前后左右的移动；录长一点 |
| 轨迹形状对、但整体偏大或偏小 | 录像太短或动作太小，尺寸估不准 | 录长一点，扫图那段多移动 |
| `notes` 里说很多帧没有地图位置 | 中途长时间对着没纹理的地方，或转开后从很不一样的位置回来 | 转开后尽量从原来的位置回来；场地多放些有花纹的东西 |
| Docker 里特别慢 | Docker Desktop 给的 CPU 太少 | 设置里给 4 核以上 |

拿不准就把这段录像的 `summary.json` 和 `logs/` 文件夹发给我们。
