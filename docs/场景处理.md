# 场景配置与排障

本页说明场景参数、批次选项、视频配对、地图复用和故障处理。首次采集按[安装与日常使用](安装与日常使用.md)完成；设备字段见[套件说明](../kits/README.md)，数据布局见[设备与坐标](设备与坐标.md)。

全部子命令、参数默认值和限制见[umi-scene 参数参考](命令行参数.md#umi-scene)；终端用 `./umi-scene <子命令> --help` 查阅。

命令行与 YAML 的职责、覆盖格式统一见[配置指南](../config/README.md)。`run / build --show-config` 只展示配置；`--dry-run` 检查输入；临时算法实验用 `--config experiment.yaml`，优先于场景内联参数，不修改场景声明。

## 配置分别写在哪里

| 文件或目录 | 管理内容 | 填写方式 |
|---|---|---|
| `kits/<套件>/kit.yaml` | 左右相机、前后镜头来源及夹爪文件路径 | 手动填写；可跨场景复用 |
| `scenes/<场景>/scene.yaml` | 处理模式、参考手和非默认参数 | 可省略；需要覆盖默认值时填写 |
| `<批次>/batch.yaml` | 本轮套件、使用手和可选复用地图 | 手动填写 |
| `<批次>/mapping/` | 本轮建图 INSV | 放置原片 |
| `<任务>/task.yaml` | 人工指令、使用手、同步和可选地图版本 | 可选；手动填写 |
| `<批次>/.pipeline/tasks/<任务>/episode.yaml` | 原片引用与身份 | 程序生成 |
| `<批次>/.pipeline/map_epochs.yaml` | 多张地图与 take 的采集顺序 | 可选；离线整理后手动填写 |

套件名来自目录且在项目内唯一；批次名在场景内唯一；任务名在批次内唯一。推荐使用 `20261105_001`、`take_001`。任务名不能使用 `cache`、`runs`、`results` 等内部目录名。

## 场景参数

默认 `shared_front` 使用一张共享工作镜头地图，支持左手、右手和双手任务。每个批次的 `mapping/` 放恰好一段建图录像，实际来源相机按 INSV 序列号识别；建图只用一只手也能处理后续双手任务。

需要调参时，复制[场景模板](../scenes/example_scene/scene.example.yaml)为 `scenes/shelf/scene.yaml`，只保留需要覆盖的字段：

```yaml
mode: shared_front
trajectory:
  video:
    frame_step: 2
```

`trajectory` 覆盖 `config/trajectory.yaml`，`parameters` 覆盖 `config/scene_parameters.yaml`，均直接填写映射。视频裁切、尺寸、编码、音轨和参数单位见[参数说明](../config/README.md)。

### 工作与环境双镜头模式

`mode: dual` 使用左右工作镜头地图和共享环境镜头地图，优先使用左右设备各自通过验收的环境镜头标定。未绑定 rear 时尝试当前 X3 INSV 工厂参数 + 本设备 front B 兜底，沿用 front 时差并标记未经 rear 独立验收，详见[标定指南](标定.md#双镜头标定与海报接入)。正式绑定在旧单来源套件填写 `rear_calibration`，双来源套件填写各自的 `calibrations.<来源>.rear`（见[来源选择](#选择内参来源)），在 `scene.yaml` 选择：

```yaml
mode: dual
reference_arm: left
```

建图原片按手放置：

```text
<批次>/mapping/
├── left/左手建图原片.insv
└── right/右手建图原片.insv
```

之后仍执行 `run <批次>`。建图阶段验收并固定工作镜头与环境镜头地图的放置、尺度和重力，设备与手的对应关系必须匹配所选地图。模式的算法差异见[算法原理](算法原理.md)。

## 批次选项

[批次模板](../scenes/example_scene/20261104_001/batch.example.yaml)列出全部用户字段：

| 字段 | 默认与要求 |
|---|---|
| `kit` | 必填；引用已有套件目录名 |
| `arms` | 默认使用套件全部手；可写非空子集，如 `[right]` |
| `map_version` | 默认按本批次 `mapping/` 建图，内容与计算条件相同时可复用；填写时明确引用已发布地图，并移走本轮建图原片 |
| `intrinsics_source` | 可选 measured/factory；覆盖套件的来源选择，CLI 开关优先，见[来源选择](#选择内参来源) |

套件只有右手时不用重复写 `arms`。双手批次缺少一手视频会保持不完整，不根据缺片改变预期使用手。

每次 `run` 都读取当前 `batch.yaml`、`kit.yaml` 和建图原片，核对测量资产并更新内部解析记录。修改相机标定、夹爪几何或建图原片后，直接重跑当前批次；运行开始时复制测量文件，历史成功结果保存当时的配置、资产副本与输入。`registry/` 只保留每个镜头、每种来源的当前测量资产。

同一批次可以保留多个已发布地图版本。需要让某个 take 使用指定版本时，在该 take 的 `task.yaml` 写 `map_version: <版本>`；它优先于批次默认地图，命令行 `--map-version` 只能与它填写相同的值。未填写时继续使用批次清单中的地图。这样可以先离线建立多个候选地图，再逐个固定任务，避免任务默认跟随“最新地图”。当前版本仍要求建图原片按批次登记；按采集时间自动划分地图 epoch 属于后续迁移阶段。

如果已经为同一批次建立了多张地图，可以在批次 `.pipeline/map_epochs.yaml` 中记录采集顺序：

```yaml
schema_version: 1
maps:
  - {epoch: epoch_001, map_version: 20261113_100000-a1b2c3d4, sequence: 0}
  - {epoch: epoch_002, map_version: 20261113_110000-e5f6a7b8, sequence: 4}
tasks:
  - {task: take_001, sequence: 1}
  - {task: take_002, sequence: 2}
  - {task: take_003, sequence: 5}
```

`sequence` 必须由采集整理结果明确提供，程序不会使用文件修改时间猜测顺序。任务选择不早于它的最近地图；例如 `take_003` 使用 `epoch_002`。地图版本必须已经发布到当前批次可访问的地图仓库；选择结果、规则和覆盖方式会写入任务的 `run_report.json`。清单只负责选择，当前阶段仍由已有 `build` 流程分别生成地图版本。

## 原片配对与补片

已确定任务归属时，把对应视频放在同一 take 的 `left/`、`right/` 中，每侧一段。程序读取内部序列号核对身份，记录 SHA256 并按内容去重，保留 take 名称和分组。缺片时补到同一任务对应侧，然后重跑。

未分组原片可放在批次 `pending/`。run 按序列号、文件名开始时间和视频时长寻找唯一配对，成功后才归入任务。默认开始时间容差 2 秒、时长差容差 1 秒，读取 `config/scene_parameters.yaml`。这些数值不修正双手时间轴，也不使用文件修改时间代替录制时间。

歧义原片继续留待确认；人工把对应视频整理到同一 take 后重跑。同一原片不能属于多个任务。其他套件设备会报告不匹配，需移出本批次或修正配置。

### 同一批次中的单手任务

如果本批次所有任务都只采右手，在 `batch.yaml` 写 `arms: [right]`。若双手批次中只有某一次操作确实仅录右手，在该任务 `task.yaml` 写（首次运行前也可填写）：

```yaml
expected_arms: [right]
```

确认实际原片只包含声明的手，再运行。`task.yaml` 不填写 `schema_version` 或 `recordings`。任务使用手必须是批次预期使用手的非空子集。指令与同步的填写方式见[训练数据指南](训练数据.md)。

### 单手任务的自动独立回退

`umi-scene run` 默认先在固定场景地图中定位。明确声明为单手的任务，如果场景定位覆盖不足、无视觉间隔过长或固定场景融合未通过质量检查，会自动尝试独立重建：用工作镜头建立本段录像的局部地图，再用 IMU 恢复米制尺度并融合。复用本次冻结的相机标定和已准备的视频、IMU，不降低独立模式的质量门限；配置过的夹爪宽度和标签中心距仍正常处理、验收。

回退成功显示 `LOCAL_OK`，结果位于 `<任务>/local_results/`，其中 `right/trajectory.csv` 或 `left/trajectory.csv` 是对应手的 TCP 轨迹。坐标编号为独立的 `local:…`，仅适用于这次录像，不能直接与其他任务叠加。查看器会标注“独立局部轨迹”且不叠加共享地图；现有共享场景验收和数据集导出不接收该结果。`results/` 仍保留原有共享结果，最新状态以 `LOCAL_OK` 为准。

相同输入重跑会复用局部结果并显示 `LOCAL_SKIPPED`；加 `--force` 会重新尝试共享定位，再按条件回退。双手任务（包括缺少一手的双手任务）、建图或地图绑定失败、标定/原片错误不会触发回退。独立重建或后续夹爪测量验收仍失败时，任务显示 `FAILED`，保留失败原因与诊断；回退并不保证一定能得到可靠轨迹。

## 标签中心距验收

套件配置了 `gripper.tag_distance` 时，每只手独立验收：有效三维标签中心距帧数与该手最终轨迹总帧数的比例默认至少 **50%**，且最长连续没有有效中心距默认不超过 **15 帧**。两枚标签均解码且三维几何检查通过才算有效，开头和结尾的缺失也计入，不插值补足。未配置标签测距的手不受此项限制。

先按轨迹时间点快速扫描整段原片，只在固定 ROI 内检测，保持原始像素分辨率；有效比例不足或存在超限长缺口时，对缺失帧执行有界补检，优先补检长缺口，两项同时达标即停止额外补检。ROI 默认 `600 980 1350 1250`，使用原始 1920×1920 工作镜头半幅的左、上、右、下坐标，补检也不越界。日志显示处理进度、速度与有效比例。参数默认值位于 `config/scene_parameters.yaml`，单个场景可在 `scene.yaml` 覆盖：

```yaml
parameters:
  tag_distance_min_valid_fraction: 0.5
  tag_distance_max_missing_frames: 15
  tag_distance_roi_px: [600, 980, 1350, 1250]
```

有效比例取值范围为 `(0, 1]`，连续缺失上限为非负整数，0 表示不允许任何缺失。恰好等于门限时通过。15 帧按最终输出帧计数，当前约 30 帧/秒时约为 0.5 秒。提高有效比例或收紧缺失上限会复用快速检测与已有补检缓存，按需继续补检；不会仅因门限变化从头识别。补检完仍不达标时任务失败，保留原片、检测缓存、旧成功结果及 `<批次>/.pipeline/tasks/<任务>/runs/failed-*/<手>/tag_distance.json` 诊断。50% 是观测覆盖要求，不代表毫米精度已经独立验证。

## 地图复用与重建

固定地图任务默认启用双向定位补全：正向定位存在缺帧时，使用同一地图反向跟踪。每个反向连续段至少需要 3 个与正向结果重叠的有效帧，全部重叠帧的位置差不超过 3 cm、旋转差不超过 3°，才补入该段的缺失帧。原有正向位姿保留；重叠不足或不一致的段仍记为缺失。所有补入帧恢复原始帧号和时间戳后再融合 IMU，原有定位覆盖率和最长中断验收继续生效。

参数来自 `config/scene_parameters.yaml` 的 `localization_*`，可在场景 `scene.yaml` 的 `parameters` 下覆盖；`localization_bidirectional: false` 可关闭补全。正向全部定位成功时不额外运行反向定位。有缺失时优先只重放包含所有缺口及两侧各 `localization_reverse_context_s` 秒的范围（默认 1 秒）；范围达到全片的 75% 时直接重放全片，短范围未完全补齐也自动退回全片。两种范围使用相同的验收门限和原始正向锚点。

成功结果在 `episode.json` 的 `arm_results.<手>.localization.<镜头>` 记录新增帧数、连续段的重叠数量、位姿差、各次反向处理范围与是否回退全片，`report.txt` 显示补全数量；失败现场保留每手的 `localization_front.json` 等诊断文件。双向一致性是内部复核，不代表已获得独立真值精度。

地图发布到 `scenes/<场景>/<批次>/.pipeline/maps/versions/<版本>/`。版本号例如 `20261105_153000-65d192ef`，使用本机开始时间和随机标识；完整输入身份保存在地图 `manifest.json`。

程序核对建图录像、设备资产、参数和算法指纹，相同输入复用已有地图。相机标定或建图原片变化会重新构建；宽度标定变化继续复用地图。夹爪几何内容计入当前建图身份，更换 TCP 几何可能触发重建。

每个批次按自身 `mapping/` 建图，只复用本批次中输入匹配的版本和缓存，不自动选择其他批次的地图。若明确需要复用同一场景内的某个已发布版本，在 `batch.yaml` 写 `map_version` 并移走本轮建图原片；程序把该版本冻结到本批次，后续不依赖来源批次。不同地图版本的坐标不保证一致。

只检查建图时可执行：

```bash
./umi-scene build scenes/shelf/20261105_001
./umi-scene build scenes/shelf/20261105_001 --force
```

`build` 只执行建图；`--force` 强制生成新版本，`--keep-work` 保留成功运行的中间数据。正常 `run` 已包含建图。高级 `run --map-version <版本>` 只覆盖该次任务处理的地图选择，下次仍读取配置；当前批次准备仍校验声明与建图输入。

建图会分别缓存录像准备、视觉地图和逐图定位，存放在 `scenes/<场景>/<批次>/.pipeline/maps/cache/`。录像准备只把原片解码为 IMU 数据和镜头视频，只随原片、视频参数、镜头列表、解码代码和 ffmpeg/numpy 版本变化；标定、ORB 参数和其他代码修改不会让同一原片重新解码，任务录像准备也共用同一规则。只调整尺度、重力或放置验收参数时，复用匹配的视觉产物并重新验收；相机模型、画面或 ORB 实现变化会使相关阶段重新计算。CLI 帮助、查看器、TCP 和夹爪测量变化不会单独触发地图重建。缓存通过文件哈希校验，损坏或不完整时重新计算，失败不会覆盖已有成功地图。

`.pipeline/` 只保留当前在用和最近一次的产物：任务成功、复用或失败后，删除被取代的运行，保留 `results` 指向的运行、最近一次尝试（可能是失败现场）和验收记录的运行；成功计算后删除本次未用到的任务缓存条目；建图成功后同样清理建图缓存。批次处理结束后删除不再被 `manifest.yaml` 或保留运行引用的地图版本，最新一次建图（含失败现场）保留。已有数据可用 `umi-scene clean <路径>` 按同样规则整理，`--cache` 清空全部缓存，见[命令行参数](命令行参数.md#clean)。

终端逐项显示阶段耗时及“复用”，地图 `manifest.json` 的 `timings` 保存同样的记录。`build --force` 跳过全部建图缓存；`--keep-work` 控制每次运行的工作目录，公共缓存独立保留，可删除后重算。升级前的地图仍可通过 `map_version` 显式使用；其清单没有完整原片内容身份，因此首次使用新复用规则时需要重新计算一次。

地图清单、尺度诊断和约束依据见[算法原理](算法原理.md#共享地图的尺度与发布条件)，结果中的地图引用见[结果说明](结果查看与验收.md#场景任务结果)。

## 批量处理与检查

```bash
./umi-scene run scenes --jobs 2
./umi-scene run scenes/shelf/20261105_001 --dry-run
./umi-scene status scenes/shelf --json
./umi-scene preflight scenes/shelf/20261105_001/take_001 --json
```

批次原片存在无法读取、设备不匹配或待补齐问题时，整批停止建图与轨迹处理；显式选择其中一个任务也遵守此规则。修正后重新运行，登记记录和旧成功结果保留。

`--jobs` 按 CPU 与内存设置。预览与实际运行共用原片规划，预览不创建清单、锁、地图、缓存或结果。它只能检查当前输入和计划，不能保证视觉建图成功。

`run --force` 跳过已完成任务的结果复用并生成新结果，中间录像准备和定位缓存仍可复用；`build --force` 强制构建新地图版本。两者保留已有成功版本。`--cores 0-7` 或 `--cores 0-3,8` 限制算法子进程可用 CPU，`--jobs` 控制任务并发数，默认 1。默认单任务调度下，双手可用核心至少 8 个时自动并行重建，并拆分两手子进程的核心范围；核心不足或 `--jobs > 1` 时两手串行，避免嵌套并行。同批任务共用本次运行已固定的地图；全部参数见 `./umi-scene run --help` / `build --help`。

原片检查包含录制模式、IMU 有效性、时间覆盖、时长、开头静止和曝光。规则来自 `config/scene_parameters.yaml`：

| 状态 | 含义与处理 |
|---|---|
| PASS | 满足当前检查规则 |
| WARN | 给出提醒并继续，如开头静止不足 |
| FAIL | 阻止处理，需修正输入 |
| UNKNOWN | 缺少判断依据，如原片没有曝光信息 |

`--skip-preflight` 供排障使用。检查通过不等于物理轨迹精度达到要求；查看、验收与导出按[结果指南](结果查看与验收.md#人工验收与导出)执行。

## 故障排查

| 问题 | 检查或操作 |
|---|---|
| 缺手、同一侧多段或配对歧义 | 核对 take 分组及内部序列号，每侧保留正确的一段原片；补片后重跑 |
| 套件或当前标定不可用 | 核对 kit.yaml 与 registry 中的来源选择；重新安装对应标定 |
| 新批次没有建图输入 | 放入 mapping 原片，或明确填写 map_version；两者不能并用 |
| 建图失败或尺度不可靠 | 查看地图版本 work 下的对齐诊断；改善平移、旋转与环境覆盖后重录 |
| 预检失败 | 查看报告中的具体检查项，按录制要求修正原片 |
| 输入变化后验收失效 | 重跑、查看新结果并重新验收 |
| 失败后仍能看到旧 results | results 保留上次成功结果；以最新处理状态判断是否有效 |

任务失败摘要和调用栈位于 `<批次>/.pipeline/tasks/<任务>/runs/<失败运行>/error.json`，原片检查报告在失败现场保留；只保留最近一次失败，更早的失败现场在下次处理后删除。成功结果按输入和算法指纹复用，阶段缓存支持重试；相同输入、相同原因的失败去重。内部文件位置见[目录参考](设备与坐标.md#目录)。

建图若连续两轮生成完全相同的候选轨迹，并因相同原因未通过验收，会显示“停止重试”，提前结束重复建图。对应地图版本目录下的 `error.json.retry` 保存比较摘要与尝试次数；各轮 `metric_alignment.json` 保留完整验收证据。固定尺度不一致时，日志会标出对应录像时间段。这个保护不会放宽尺度/重力门限，也不代表该段录像已被修复。

## 选择内参来源

套件用 `intrinsics.front/rear` 分别选择 measured / factory，自动解析当前参数（见 [套件配置](../kits/README.md#前后镜头独立选择来源)）。批次可设置：

```yaml
kit: kit_001
intrinsics_source: factory
```

也可执行 `./umi-scene run <批次> --intrinsics-source factory` 或 `./umi-scene build <批次> --intrinsics-source factory`。命令行和批次的统一选择覆盖 kit 的两镜头设置；通常省略这两处，只在 kit 配置 `intrinsics.front/rear`，默认分别为 measured/factory。旧套件的 `calibration` / `rear_calibration` 继续固定原版本，显式开关仅核对来源，不会自动替换版本。

选择解析为各相机的具体版本后存入批次记录和不可变快照。切换来源时保留旧地图/任务结果，构建或查找匹配新参数的独立地图；`--map-version` 也必须与来源和完整参数配套。front 缺少所选来源的完整参数会报错；rear factory 尚未登记时按原片推导并明确标记未独立验收。旧地图若由之前的 ORB 库生成，会按引擎身份检查要求重建。
